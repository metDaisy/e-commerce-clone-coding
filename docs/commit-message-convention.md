# 커밋 메시지 및 커밋 단위 규칙

이 문서는 이 저장소의 Git 커밋 메시지 형식과 커밋을 나누는 기준을 정의한다.

## 기준의 출처

커밋 단위와 메시지 작성의 기본 방향은 Google Engineering Practices의 다음 원칙을 반영한다.

- 하나의 커밋은 **self-contained change**여야 하며, 한 가지 목적만 해결한다.
- 변경에 필요한 관련 테스트는 같은 커밋에 포함한다.
- 리팩터링·기능 변경·버그 수정은 가능한 한 별도 커밋으로 나눈다.
- 큰 변경은 파일·계층·기능 단위의 여러 커밋으로 나누고, 의존성이 있으면 순서대로 쌓는다.
- 첫 줄은 짧고 구체적인 명령형 요약으로 작성하고, 본문은 변경의 맥락과 이유를 설명한다.

이 저장소의 `type:` 접두사, 50자 제한, `--- 본문 ---` 및 `--- 관련 이슈 ---` 헤더는 Google 전체의 공통 강제가 아니라 이 저장소에서 추가한 확장 규칙이다. Google 공식 문서에는 일반적인 고정 글자 수 제한이 없지만, 이 저장소는 AOSP의 50자 headline 관례와 기존 자동 검증을 고려해 50자 제한을 유지한다.

참고 문서:

- [Google Engineering Practices: Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)
- [Google Engineering Practices: Writing good CL descriptions](https://google.github.io/eng-practices/review/developer/cl-descriptions.html)
- [AOSP: Submit code changes](https://source.android.com/docs/setup/contribute/submit-patches)

## 기본 원칙

- 하나의 커밋은 하나의 논리적 변경만 포함한다.
- 커밋은 독립적으로 검토하고 되돌릴 수 있는 단위로 만든다.
- 파일 개수가 아니라 변경의 목적과 결합도를 기준으로 커밋을 나눈다.
- 최상위 관심사(`src`, `docs`, `.hermes`, 빌드 설정)가 다르면 먼저 별도 커밋을 검토한다.
- 서로 관계없는 기능·버그 수정·리팩터링·문서 변경을 하나의 커밋에 섞지 않는다.
- 리뷰어가 변경의 맥락을 파악할 수 있도록 커밋 설명만으로 무엇을 왜 바꾸었는지 이해할 수 있어야 한다.
- 커밋하기 전에 staged diff를 확인하고, 메시지는 실제 staged 변경을 근거로 작성한다.
- 사용자가 명시적으로 요청하지 않은 commit, amend, push, merge, rebase, reset은 실행하지 않는다.

## 커밋을 나누는 기준

### 하나의 커밋으로 묶는 경우

다음 변경은 하나의 논리적 결과를 만들기 위해 함께 필요한 경우 같은 커밋에 포함한다.

- 기능 구현 코드와 그 기능을 검증하는 테스트
- 버그 수정 코드와 재현·회귀 테스트
- API 계약 변경과 서버 구현·관련 테스트
- 도메인 규칙 변경과 해당 규칙의 단위·통합 테스트
- 코드가 반드시 요구하는 Flyway 마이그레이션과 해당 코드 변경
- 하나의 사용자 기능을 완성하는 백엔드와 프런트엔드 변경

### 별도의 커밋으로 나누는 경우

다음 변경은 독립적으로 검토할 수 있다면 분리한다.

- 동작 변경이 없는 리팩터링과 기능 구현
- 동작 변경이 없는 포맷팅·스타일 수정
- 기존 동작을 검증하는 독립적인 테스트 추가와 기능 구현
- 테스트 구조 리팩터링과 제품 코드 변경
- 기능과 무관한 문서·오타·링크 수정
- 독립적인 백엔드 작업과 프런트엔드 작업
- 서로 다른 이슈나 서로 다른 비즈니스 목적에 속한 변경
- 의존성·빌드 설정 변경과 기능 변경이 서로 독립적인 경우

단순히 파일 하나마다 커밋을 만들지는 않는다. 반대로 여러 작업을 하나의 거대한 커밋으로 합쳐서 변경 목적과 검증 범위를 알 수 없게 하지 않는다. 특히 `docs`와 `.hermes`처럼 최상위 관심사가 다른 변경은 서로의 동작에 직접 필요한 경우가 아니면 분리한다.

## 권장 분할 단위

커밋을 만들기 전에 변경 파일을 다음 순서로 하나의 change set으로 분류한다.

1. **목적**: 같은 사용자 요구·버그·구조 개선을 해결하는가?
2. **결합도**: 한쪽을 되돌리면 다른 쪽이 컴파일·테스트·문서 계약상 반드시 깨지는가?
3. **검증 범위**: 같은 테스트·정적 검사로 결과를 판정할 수 있는가?
4. **관심사**: 같은 모듈·문서 영역·도구에 속하는가?

다음은 이 저장소에서 사용하는 기본 분할 예시다.

| 변경 범위 | 기본 커밋 단위 | 분리 판단 |
|---|---|---|
| `src/main`과 해당 기능의 `src/test` | 기능 또는 버그 단위 | 테스트가 해당 구현 없이는 의미가 없으면 함께 묶는다. |
| `docs/requirement/p2/**` | P2 요구사항 단위 | P2 안에서도 서로 다른 비즈니스 목적이면 다시 나눈다. |
| `docs/requirement/p9/**` | P9 요구사항 단위 | 다른 요구사항 영역과 섞지 않는다. |
| `docs/adr/**` | 하나의 아키텍처 결정 단위 | 서로 다른 결정 번호는 기본적으로 나눈다. |
| `.hermes/plugins/agent-audit/**` | plugin 기능 단위 | manifest·구현·plugin 회귀 테스트처럼 함께 필요한 파일은 묶는다. |
| `docs/**`와 `.hermes/**` | 기본적으로 별도 커밋 | plugin 계약을 설명하는 문서라도 구현과 독립적으로 검토 가능하면 분리한다. |

디렉터리가 같다는 이유만으로 자동으로 묶지 않는다. 반대로 하나의 요구사항을 설명하는 여러 문서가 같은 검증 기준과 변경 목적을 공유한다면 여러 파일이어도 하나의 커밋으로 묶을 수 있다.

### 큰 커밋을 분리하는 예

`59debf69d012dc5117627c7bf1bd66b0828f4927`은 다음처럼 나누는 편이 더 적절했다.

- `docs/requirement/p2/**`의 P2 관련 변경 → P2 요구사항 문서 커밋
- `docs/requirement/p9/**`의 P9 관련 변경 → P9 요구사항 문서 커밋
- `.hermes/plugins/agent-audit/**`와 이에 반드시 필요한 `.hermes/README.md` → `agent-audit` plugin 커밋
- `docs/validator-contract.md` → validator 계약 문서 커밋
- `docs/architecture.md`, ADR, `docs/index.md` 등의 구조 문서 → 각 결정·문서 목적에 따른 문서 커밋
- `.gitignore`, `AGENTS.md`, `README.md` 등 저장소 운영 규칙 변경 → 각각의 목적에 맞는 별도 문서·설정 커밋

위 목록은 파일을 기계적으로 하나씩 나누라는 뜻이 아니다. 각 묶음은 **한 문장으로 목적을 설명할 수 있고, 독립된 검토·검증·되돌리기가 가능한지**를 확인한 뒤 확정한다. plugin 구현과 plugin 회귀 테스트처럼 강하게 결합된 파일은 같은 커밋에 남긴다.

### staged diff 분할 절차

- `git status --short --untracked-files=all`로 기존 변경과 새 변경을 먼저 구분한다.
- change set별로 `git add <paths>`를 실행하고, 필요한 경우 `git add -p`로 한 파일 안의 독립된 hunk도 분리한다.
- `git diff --cached --name-only`로 staged 파일 목록을 확인한다.
- `git diff --cached`를 읽고 모든 hunk가 같은 목적에 속하는지 확인한다.
- `git diff --cached --check`와 해당 change set의 가장 가까운 테스트·정적 검증을 실행한다.
- 검증 범위나 커밋 목적을 한 문장으로 설명하지 못하면 더 나누거나 결합 근거를 본문에 남긴다.

커밋 간 의존성이 있으면 기반 문서·계약, 구현, 테스트·검증 보완 순서로 정렬한다. 단, 앞 커밋만 checkout해도 저장소가 불필요하게 깨지지 않도록 가능한 범위에서 각 커밋을 실행 가능한 상태로 유지한다.

Google 문서에는 커밋 크기에 대한 절대 기준이 없다. 이 저장소에서도 파일 수나 줄 수만으로 실패시키지 않는다. 다만 리뷰어가 변경을 빠르게 이해하기 어려울 정도로 크거나, 여러 목적·검증 범위가 섞인 경우에는 작은 커밋으로 다시 나눈다. 판단이 애매하면 큰 커밋보다 작은 커밋을 우선한다.

## 변경 유형별 검증 범위

모든 커밋이 저장소의 모든 검증기를 통과해야 하는 것은 아니다. 검증기는 변경 경로와 변경 목적에 따라 적용한다. 적용 대상이 아닌 Rule은 `not_required`로 보고하며, 필요한 Rule을 실행하지 않은 `not_run`과 구분한다.

| 변경 유형 | 기본 검증 | 적용하지 않는 검증의 예 |
|---|---|---|
| Markdown 문서만 변경 | `git diff --check`, Markdown 내부 링크·경로 검사, 문서 사실관계·참조 확인 | Java Checkstyle, Gradle 테스트, Modulith·ArchUnit |
| Java 소스·테스트 변경 | `checkstyleMain`, `checkstyleTest`, 관련 JUnit, 변경 범위에 따른 Modulith·ArchUnit | 변경과 무관한 문서 전용 검사 |
| `.hermes` plugin 변경 | Python compile·plugin 회귀 테스트, manifest 변경 시 Plugin Doctor·runtime 확인 | Java 전용 검증 |
| 문서와 소스가 함께 변경 | 각 변경 유형의 검증을 모두 실행 | 해당 없는 Rule만 제외 |

Markdown 문서가 `docs/validator-contract.md`처럼 실행 규칙·공개 계약을 설명하는 경우에는 문서 검사만으로 끝내지 않고, 변경된 계약을 구현·테스트가 따르는지 관련 검증을 추가한다. 반대로 `docs/requirement/p2/**`와 같은 요구사항 문서만 변경하고 제품 동작을 변경하지 않았다면 Java·Gradle 검증을 억지로 실행하지 않는다. 요구사항 변경을 구현하는 작업은 문서 커밋과 별도의 구현 커밋으로 나누고, 구현 커밋에서 소스 범위의 검증을 수행한다.

문서 link checker가 아직 연결되지 않은 Rule은 성공한 것으로 간주하지 않는다. 현재 `DOC-LINK-001`은 계약상 예약 Rule이므로, 전용 checker가 연결되기 전에는 `agent-audit`의 자동 요구 대상이 아니다. 다만 문서 workflow 또는 CI에 연결된 결정론적 검사가 있으면 그 결과를 기록하고 실패를 수정한다.

## 커밋의 품질 기준

각 커밋은 가능한 한 다음 조건을 만족해야 한다.

- 저장소를 알려진 고장 상태로 남기지 않는다.
- 관련 테스트와 정적 검증을 통과하거나, 통과하지 못했다면 그 이유를 명확히 남긴다.
- 임시 로그, 디버깅 코드, 사용하지 않는 import, 생성된 임시 파일을 포함하지 않는다.
- 요청 범위 밖의 변경을 포함하지 않는다.
- 이전 커밋에 이미 포함된 변경을 의미 없이 반복하지 않는다.
- 커밋 순서만으로 변경의 의존 관계를 이해할 수 있어야 한다.

불가피하게 중간 커밋이 완전하게 검증될 수 없다면, 최종 결과에 도달하기 위한 의존 순서를 유지하고 메시지 또는 작업 보고에서 제한 사항을 설명한다.

## 커밋 Type

첫 줄은 다음 형식으로 작성한다.

`<type>: <subject>`

허용하는 Type은 다음과 같다.

| Type | 사용 기준 |
|---|---|
| `feat` | 새로운 사용자·시스템 기능 추가 |
| `fix` | 잘못된 동작이나 버그 수정 |
| `docs` | 문서만 변경 |
| `style` | 로직 변경 없는 포맷·스타일 수정 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `test` | 제품 코드 변경 없이 테스트 추가·수정 |
| `chore` | 빌드·의존성·도구·패키지 설정 등 로직 외 작업 |

`type:` 접두사는 이 저장소의 분류 규칙이다. Google의 CL 설명에는 이 접두사가 필수는 아니지만, 이 저장소에서는 변경 목적을 빠르게 식별하기 위해 사용한다. 기능 수정에 테스트를 함께 포함한 경우에는 `test`가 아니라 `feat` 또는 `fix`를 사용한다. 기존 동작을 검증하는 독립적인 테스트만 변경한 경우에만 `test`를 사용한다.

## Subject 규칙

- Subject는 한국어로 작성한다. Type과 코드·클래스·API 식별자는 원문을 유지할 수 있다.
- 첫 줄 전체(`type: subject`)를 공백 포함 50자 이내로 작성한다.
- Google식 명령형 문장으로, 변경된 결과가 아니라 수행한 변경을 간결하게 표현한다.
- 변경의 핵심 목적이 드러나야 하며, `수정`, `작업`, `변경`처럼 의미가 모호한 표현만 사용하지 않는다.
- 문장 끝에 마침표를 붙이지 않는다.
- 꺾쇠 괄호(`<`, `>`)를 실제 메시지에 포함하지 않는다.

예시:

`feat: 초기 상품 카탈로그 모델 추가`

`fix: 기본 배송지 삭제 후 승격 오류 수정`

`docs: 개발 문서 기준과 검증 절차 정리`

## 본문 규칙

본문은 변경의 세부 내용과 이유를 설명할 필요가 있을 때 작성한다. 단순하고 자명한 변경은 본문을 생략할 수 있지만, 여러 파일·계층·문서 영역에 걸친 변경은 가능한 한 본문을 작성한다.

본문은 Subject 다음에 빈 줄 하나를 두고 시작한다. 이 저장소에서는 본문을 쉽게 식별하기 위해 다음 헤더를 사용할 수 있다.

`--- 본문 ---`

- Google식으로 본문은 자유로운 문단 또는 목록으로 작성할 수 있다. `- ` 목록은 선택 사항이다.
- 무엇을 변경했는지(**what**)와 왜 변경했는지(**why**)를 우선 설명한다.
- 리뷰어가 알아야 하는 설계 배경, 영향 범위, 제한사항, 후속 작업이 있으면 덧붙인다.
- 검증 결과를 작성할 때는 실제 실행한 명령과 결과만 기록한다.
- 본문이 없으면 `--- 본문 ---` 헤더도 작성하지 않는다.
- 확인되지 않은 효과나 실행하지 않은 검증 결과를 적지 않는다.

예시:

```text
feat: 카탈로그 상품 식별자 검증 추가

--- 본문 ---
CatalogProduct 생성과 갱신 요청의 식별자 형식을 검증한다.

잘못된 형식과 중복 식별자를 필드별 오류로 반환해 클라이언트가 수정할 수 있도록 한다.
```

## 관련 이슈 규칙

Issue 번호가 사용자 요청이나 작업 메타데이터에서 명시적으로 제공된 경우에만 관련 이슈를 포함한다.

- 브랜치명·파일명·과거 커밋만으로 Issue 번호를 추론하지 않는다.
- 관련 이슈를 포함할 때는 다음 헤더를 정확히 사용한다.
- Action은 실제 관계에 맞게 작성한다. 예: `close`, `fix`.

```text
--- 관련 이슈 ---
fix: #123
```

Issue 번호가 확인되지 않으면 `--- 관련 이슈 ---` 헤더를 추가하지 않는다.

## 전체 형식

본문과 Issue가 모두 있는 경우:

```text
<type>: <subject>

--- 본문 ---
- 무엇을 변경했는지 설명한다.
- 변경 이유 또는 영향 범위를 설명한다.

--- 관련 이슈 ---
<Action>: #<Issue Number>
```

본문만 있는 경우에는 관련 이슈 헤더를 생략한다. 본문과 Issue가 모두 없으면 첫 줄만 작성한다.

## Agent가 커밋 메시지를 작성할 때

- 먼저 `git diff --cached`로 staged 변경을 확인한다.
- staged 변경이 없으면 작업 트리의 diff를 확인하고, 어떤 변경을 대상으로 하는지 명시한다.
- diff를 확인하지 않고 Type·Subject·Issue를 추측하지 않는다.
- 사용자가 커밋 메시지만 요청한 경우 실제 commit을 실행하지 않는다.
- 최종 출력은 규칙에 맞는 raw 커밋 메시지만 반환한다. 설명, Markdown 코드 블록, 추가 안내를 붙이지 않는다.
