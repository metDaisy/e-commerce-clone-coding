# P5 Order Session

OrderSession은 사용자가 여러 디바이스에서 로그인할 수 있는 환경에서, 하나의 `PENDING` 주문 화면과 결제 요청을 한 디바이스로 제한하기 위한 임시 점유 정보다. 업무 주문 데이터는 [Order API](p5-order.md), 전체 정책은 [P5 Policy](p5-policy.md)를 따른다.

## 1. 범위와 책임

- 하나의 사용자·주문에 하나의 유효한 디바이스만 허용
- 주문 화면 조회·갱신·결제 요청 API 보호
- 브라우저 쿠키와 Caffeine 인메모리 캐시 관리
- 브라우저 종료 요청을 받지 못한 경우의 만료 처리

OrderSession은 주문 이력이나 결제 데이터가 아니다. 단일 인스턴스 개발 범위에서는 JPA에 저장하지 않고 Caffeine에만 저장한다. 인스턴스가 내려가면 세션은 모두 초기화되며, 주문 자체는 DB에 남는다.

## 2. 데이터 모델

| 필드 | 타입 | 필수 | 설명 |
|---|---|---:|---|
| `userId` | UUID | O | 세션 소유자 |
| `orderId` | UUID | O | 점유 중인 `PENDING` 주문 |
| `deviceId` | String | O | 서버가 발급한 디바이스 식별자 |
| `tokenHash` | String | O | 쿠키 원문 대신 저장하는 해시 |
| `expiresAt` | Instant | O | 마지막 허용 활동으로부터 30분 후 |

`status`와 `lastSeenAt`은 저장하지 않는다. 캐시에 존재하고 `expiresAt`이 현재 시각보다 미래이면 유효한 세션으로 판단한다. `expiresAt`이 지나면 캐시 항목을 제거한다.

## 3. 토큰과 쿠키

### 3-1. `checkout_token` 발급

서버는 예측할 수 없는 고엔트로피 난수를 생성해 쿠키 원문으로 발급한다. 서버에는 다음과 같이 저장한다.

```text
tokenHash = SHA-256(serverSecret + ":" + checkoutToken)
```

비교할 때도 요청 쿠키를 같은 방식으로 해시해 Caffeine 값과 비교한다. 데이터베이스 조회 없이도 서버가 현재 유효한 세션과 폐기 여부를 직접 통제할 수 있고, 캐시가 탈취되어도 쿠키 원문이 노출되지 않는다.

JWT를 사용하지 않는 이유는 OrderSession이 사용자·주문·디바이스의 서명된 주장보다 서버가 즉시 폐기하고 점유 충돌을 판정해야 하는 짧은 상태이기 때문이다. Refresh Token은 여러 요청에서 검증 가능한 만료·주장을 담고 갱신 정책을 적용하기에 JWT를 사용할 수 있지만, OrderSession에는 서버 측 상태가 필요하므로 불투명 토큰과 해시가 적절하다.

### 3-2. 쿠키 속성

```text
Name:     checkout_token
Path:     /
HttpOnly: true
Secure:   true
SameSite: Lax
Max-Age:  1800
```

`Path=/`로 설정해 주문 화면 API뿐 아니라 다른 화면의 API에도 쿠키가 전달되도록 한다. 주문 화면 API가 아닌 API는 세션을 사용하지 않으며, 응답에서 삭제 쿠키를 내려 브라우저에 남은 토큰을 정리할 수 있다. 프론트엔드 스크립트는 `HttpOnly` 쿠키를 직접 삭제하지 않는다.

## 4. 허용 API와 만료 연장

OrderSession을 사용할 수 있는 API를 화이트리스트로 관리한다.

| API | 용도 | 활동 인정 | `expiresAt` |
|---|---|---:|---|
| `GET /api/v1/orders/{orderId}` | 주문 화면 조회 | 예 | 30분 연장 |
| `POST /api/v1/orders` | 주문 생성·갱신 | 예 | 30분 연장 |
| `GET /api/v1/me/addresses` | 주소 선택 | 예 | 30분 연장 |
| `GET /api/v1/payment-methods` | 결제 수단 조회 | 예 | 30분 연장 |
| `POST /api/v1/payment-methods` | 결제 수단 등록 | 예 | 30분 연장 |
| `DELETE /api/v1/payment-methods/{id}` | 결제 수단 삭제 | 예 | 30분 연장 |
| `GET /api/v1/payments/{paymentId}` | 결제 처리 상태 조회 | 예 | 30분 연장 |
| `POST /api/v1/orders/{orderId}/pay` | 결제 요청 | 예 | 30분 연장 |

화이트리스트 밖의 API는 OrderSession을 사용하지 않는다. 해당 요청에 `checkout_token`이 있으면 세션 삭제 쿠키를 내려 브라우저 토큰만 정리하며, 다른 디바이스의 세션을 삭제하지 않는다.

## 5. 동시 접속과 충돌

1. 디바이스 A가 주문 화면을 열면 `(userId, orderId)`에 A의 `tokenHash`를 저장한다.
2. 디바이스 B가 같은 주문 화면 또는 결제를 요청하면 B의 토큰이 일치하지 않아 `423 ORDER-018`을 반환한다.
3. 디바이스 ID를 요청 본문으로만 믿지 않는다. 공격자가 A의 ID를 알아도 A의 HttpOnly 쿠키 원문과 `tokenHash`를 갖지 못하면 통과할 수 없다.
4. 세션 획득·갱신은 Caffeine의 원자적 연산으로 처리해 동일 시점의 두 요청이 동시에 점유하지 않도록 한다.

## 6. 생성·갱신·삭제

- 주문 화면 진입 시 세션을 생성하고 쿠키를 발급한다.
- 화이트리스트 API에 유효한 요청이 들어오면 처리 성공 후 `expiresAt = now + 30분`으로 갱신한다.
- 결제 성공·주문 취소·주문 만료 시 Caffeine에서 해당 주문 세션을 제거하고 삭제 쿠키를 반환한다.
- 사용자가 장바구니 화면에 도착하면 장바구니 응답에서 삭제 쿠키를 반환한다. 다른 디바이스의 세션은 유지한다.
- 정상적인 브라우저 종료를 서버가 반드시 감지한다고 가정하지 않는다. 강제 종료·크래시·전원 차단은 최대 30분 동안 세션이 남을 수 있다.

하트비트는 사용하지 않는다. 주문 화면에서 아무 동작도 하지 않는 사용자의 세션을 계속 연장하지 않고, 실제 허용 API 요청이 있을 때만 연장한다.

## 7. 예외

| HTTP | exceptionCode | 발생 조건 | client message |
|---:|---|---|---|
| 401 | `ORDER-015` | 토큰이 위조·불일치 | 주문 화면 세션이 유효하지 않습니다. |
| 404 | `ORDER-016` | 세션이 없음 | 주문 화면을 다시 열어주세요. |
| 410 | `ORDER-017` | `expiresAt` 경과 | 주문 화면 세션이 만료되었습니다. |
| 423 | `ORDER-018` | 다른 디바이스가 점유 중 | 다른 기기에서 주문이 진행 중입니다. |
